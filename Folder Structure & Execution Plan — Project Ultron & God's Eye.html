2. Dependency Graph (why the phase order below is correct)

shared/  ──►  database/
                  │
                  ▼
              sensors/  ──►  core/  ──►  shields/  ──►  range_simulator/
                  │             │            │
                  └─────────────┴────────────┴──►  ui/  (consumes ui_bus from all of them)

ui/ is deliberately last even though it's the most visually impressive part — every frame is just a dumb renderer of messages that other modules push onto ui_bus. Building it first would mean building it against fake data, then rewiring it later. Building it last means it's wired against the real pipeline from the first line of code.

3. Step-by-Step Execution Plan

Step Module(s) Deliverable Can be demoed standalone?
1 shared/event_bus.py, shared/logger.py Two working queues + logging setup No — pure plumbing
2 database/schema.sql, database/manager.py, database/models.py DatabaseManager that boots, creates tables, accepts a test write/read Yes — insert a fake row, read it back
3 sensors/arp_scanner.py Scapy sweep pushing real asset data into event_bus and network_assets Yes — run it, watch rows appear in ultron.db
4 sensors/canary_monitor.py, sensors/honeypot_listener.py Remaining two sensors, same pattern Yes — touch a canary file, watch the event
5 core/agent_client.py, core/schemas.py Antigravity Agent wired with system instructions + policy hooks, returns validated JSON for a hardcoded test payload Yes — call it directly with a sample telemetry batch
6 core/correlator.py, core/risk_scoring.py, core/mitre_lookup.py, core/brain.py Full consumer loop: real sensor events → correlated batch → agent → logged incident Yes — run sensors + brain together, watch incidents table populate
7 shields/base.py, shields/linux_shield.py, shields/windows_shield.py, shields/privilege_check.py Real firewall/process containment wired to brain.py's recommended_action Yes — trigger a real (safe, loopback) block and see the OS-level rule appear
8 shields/quarantine.py Host quarantine mode Yes
9 range_simulator/* Three loopback-only attack scripts Yes — this is what proves Steps 3–8 actually work end to end
10 ui/theme.py, ui/main_window.py, all ui/panels/* Full dashboard wired to ui_bus, poll loop draining real events Yes — this is the full live demo
11 ui/voice_alerts.py pyttsx3 worker thread for critical alerts Yes
12 main.py, config.py Final wiring: boot order, thread startup, graceful shutdown This is the actual python main.py that runs the whole thing

Why this order and not UI-first: Steps 1–9 are each independently testable from the terminal/DB without any GUI — that means by the time you reach Step 10, every bug in sensors, the agent contract, or shield execution has already been caught and fixed against real data. The dashboard then becomes a thin, low-risk layer at the very end instead of the thing you're debugging blind under time pressure the night before the demo.

Suggested stopping points if time runs short: Steps 1–9 alone already satisfy a live terminal-based demo of full detect→reason→contain (you can literally print() from brain.py and shields/). Step 10 is what makes it look like a SOC command center for judges — prioritize it once 1–9 are solid, not before.
