How It Works

Project Ultron & God's Eye — End-to-End Walkthrough & Pitch Notes

Companion docs: PRD v1.0, TRD v1.0, UI/UX Blueprint v1.0, DB Schema & DAO v1.0, Execution Plan v1.0

1. The System in One Paragraph

An attacker touches your network in some way — probes a port, tries to brute-force SSH, or messes with a file. God Eye's sensors (running quietly on background threads) catch that signal the instant it happens and drop it, as a small JSON event, onto a shared queue. Ultron's Brain — a single loop powered by the google-antigravity AI agent — picks that event up, figures out what it actually means (how dangerous, what kind of attack, MITRE classification), and decides what should be done about it. The Shields then execute that decision at the OS level — blocking the IP or killing the process — usually in well under half a second. Every single step of this, from the first probe to the final block, is written to a local SQLite database, so nothing is ever a black box: you can always answer "what happened, when, and why did the system respond the way it did."

2. Walkthrough — A Real Attack, Traced Through Every Module

Scenario: an unauthorized machine on the network attempts an SSH brute-force against your host.

  1. God Eye notices. sensors/arp_scanner.py already flagged this device's MAC address as unrecognized the moment it joined the subnet — that alone created a LOW severity telemetry row. Now, sensors/honeypot_listener.py (or your real auth.log tail, depending on final scope) sees repeated failed authentication attempts from that same IP in rapid succession. Each attempt becomes a telemetry_events row: {source_module: "HONEYPOT", suspicious_ip: "192.168.1.203", raw_payload: {...}}.

  2. The events queue up. These rows don't go straight to the AI one at a time — shared/event_bus.py's queue holds them, and core/correlator.py waits for a short correlation window so that 8 failed-login attempts in 3 seconds become one batched payload instead of 8 separate, noisy incidents.

  3. Ultron reasons about it. core/brain.py hands that batch to the google-antigravity Agent. The agent doesn't get to touch your firewall or kill anything itself — its only job is to return the structured verdict: risk_score: 91, severity: "CRITICAL", mitre_id: "T1110", mitre_tactic: "Credential Access", summary: "Repeated SSH auth failures from unauthorized host 192.168.1.203", recommended_action: "firewall_block". This gets written to incidents immediately — the reasoning is on record even before anything is done about it.

  4. A decision gets made about enforcement. If config.RESPONSE_MODE == AUTONOMOUS, brain.py calls shields/linux_shield.py (or windows_shield.py) right away. If it's HUMAN_APPROVAL mode, a shield_actions row is written as PENDING instead, and the dashboard lights up a "Deploy Shield" button for a human to click.

  5. The Shield acts. iptables -A INPUT -s 192.168.1.203 -j DROP runs via subprocess. The time between step 1 (first detection) and this line executing is measured with time.perf_counter() — that's your headline "contained in 118ms" number.

  6. Everything lands in the dashboard. While all of this was happening, every module was also pushing a message onto ui_bus. The Radar panel already showed this device with a red "ROGUE" marker from step 1. The Brain Feed panel streamed the raw JSON reasoning output live as it arrived in step 3. The Shield Log shows the block with its latency the instant step 5 completes. None of the UI code decided anything — it only ever renders what already happened elsewhere, which is why the dashboard can never desync from what the system actually did.

  7. It's all still there afterward. Because incidents and shield_actions are append-only, you can open the app an hour later, click that incident, and reconstruct the entire chain — first sighting, AI reasoning, and containment action — from the database alone, with no live agent needed to explain it.

3. What Makes Each Layer Trustworthy (not just functional)

  • Detection is dumb on purpose. Sensors never interpret anything — they just observe and normalize. This means a sensor bug can produce noisy data, but it can never accidentally decide to block someone.
  • The AI reasons, it never acts. This is the single most important design decision in the whole system (Section 4 of the TRD) — google-antigravity's policy hooks technically prevent the agent from calling anything except two read-only lookups. Every containment action is a deterministic function call in shields/, triggered by code you wrote and can read, not by whatever the model decided to do on a given inference.
  • Shields are the only code with execution authority, and even they respect a human-approval mode — so the "autonomous" part of the pitch is a configurable dial, not an unconditional claim.
  • Storage never lies retroactively. No row's core findings (risk_score, summary, latency_ms) are ever overwritten — only status fields transition. What the system decided in the moment is what the database still says a week later.

Running all three back-to-back in front of judges is the strongest proof point: three genuinely different attack shapes, correctly classified and correctly contained, with real timing numbers on screen — not a scripted fake.

5. Likely Judge Questions & Straight Answers

  • "Is the AI actually deciding to block things, or is that hardcoded?" → The agent produces the risk score, MITRE tag, and recommended action; whether that recommendation gets executed automatically or held for approval is a config toggle. The execution code itself is deterministic and auditable — that's intentional, not a limitation.
  • "What stops this from blocking a legitimate device by mistake?" → is_authorized on network_assets, the correlation window (so a single stray packet doesn't trigger anything), and the HUMAN_APPROVAL mode as a safety valve for exactly this concern.
  • "Does this need the internet to work?" → Detection and containment are fully local. Only the Antigravity/Gemini reasoning call goes outbound; everything else — sensors, database, shields, UI — runs air-gapped.
  • "Why SQLite and not a real database server?" → Zero-config, single-file, no server process to secure or crash — appropriate for a single-host defense agent, and WAL mode gives it real concurrent read/write behavior despite being "just a file."
