3. Thread Safety: How Background Threads Update This UI

customtkinter (like all Tkinter) is not thread-safe — any widget mutation from a thread other than the main loop's thread risks a crash or a silently corrupted UI. This dashboard avoids that with a single rule: background threads never touch a widget. Ever.

The mechanism:

  1. shared/event_bus.py exposes two queues, not one: sensor_queue (sensors → brain, per the TRD pipeline) and ui_bus (everything → UI). Every subsystem — sensors, the brain, shields — pushes a small serializable dict describing what changed onto ui_bus (e.g. {"type": "asset_update", "mac": "...", "authorized": False}), never a widget reference, never a direct call into ui/.
  2. UltronDashboardApp._start_poll_loop is the only code that reads ui_bus, and it runs via self.after(100, self._start_poll_loop) — a Tkinter-native mechanism that schedules its own callback back onto the main event loop, so it always executes on the same thread that owns every widget. This is the standard, safe pattern for Tkinter + background work (the alternative, calling .event_generate() from a worker thread, is more fragile and unnecessary here).
  3. Each tick, the poll loop drains everything currently sitting in ui_bus (non-blocking get_nowait() in a loop until queue.Empty) and fans each message out to the right frame's update_*/append_* method. Because this dispatch happens inside the .after() callback, every widget mutation is guaranteed to happen on the main thread — sensors, the Antigravity agent call, and shield execution can all take as long as they need on their own threads without ever freezing the window.
  4. Button clicks flow the opposite direction safely for free: Tk callbacks (_handle_click, _handle_switch_toggled) already run on the main thread by construction, so they can immediately call back into the controller (on_simulate, on_toggle_response_mode) — the controller is then responsible for kicking that work onto a background thread if it's not instant (e.g. on_simulate starts the range_simulator/ scenario on its own threading.Thread, it doesn't run the attack script inline in the click handler).

Net effect: the 100ms poll tick is the only seam between "many background threads doing real work" and "one Tkinter main loop that must never block," and it's small/cheap enough that it doesn't visibly compete with the 500ms containment-latency budget.
