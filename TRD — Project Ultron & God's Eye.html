Technical Requirement Document

Project Ultron & God's Eye — Autonomous SOC Agent

Version: 1.0 | Audience: Engineering team | Companion doc: PRD v1.0

1. System Boundaries

Boundary Inside Outside
Trust boundary Sensors, Ultron Brain, Shields, SQLite — all run in-process, same host Antigravity/Gemini API call (reasoning only, no execution rights)
Execution authority Only shields/ may invoke subprocess, psutil.kill, or firewall commands core/ (the agent) may only recommend; it never gets raw OS access
Network exposure Honeypot listener (intentionally exposed), ARP scanner (read-only) No inbound ports besides the honeypot; UI/DB never network-exposed
Data boundary All telemetry/incidents persist locally in SQLite No telemetry leaves the host except the JSON payload sent to the Antigravity/Gemini reasoning call

This is the core architectural rule the whole TRD hangs on: sensors observe, the agent decides, shields act, storage records — and no module skips a layer.

2. Data Flow Pipeline

[Scapy ARP thread]   ─┐
[Watchdog canary thread]├─► event_bus.Queue (thread-safe) ─► [Ultron Brain loop] ─► decision
[Honeypot socket thread]─┘                                         │
                                                                    ├─► shields/* (if action_required)
                                                                    └─► storage/db.py (always, every step)

Step-by-step contract:

  1. Ingestion (async, non-blocking): each sensor runs on its own threading.Thread(daemon=True). A sensor's only job is to normalize a raw signal into a single JSON schema and queue.put() it. Sensors never inspect each other's data and never call the agent directly.
  2. Cognition: a single consumer thread (ultron_core/brain.py) runs queue.get() in a loop, batches/windows correlated events (same suspicious_ip within N seconds), and calls the google-antigravity Agent with the batched payload. The agent's system instructions constrain its output to a fixed JSON contract (Section 4). The agent is never given a tool that executes anything — its "tool calling" surface is limited to read-only lookups (MITRE table, historical incident count for scoring); actual response actions come back as a recommendation field, not a tool invocation.
  3. Enforcement: the brain thread reads recommended_action from the agent's structured output. If config.RESPONSE_MODE == AUTONOMOUS, it calls the matching function in shields/ directly. If HUMAN_APPROVAL, it writes a PENDING row and the UI exposes a "Deploy Shield" button that, on click, calls the same shield function. Either path measures t_detected → t_contained and logs latency_ms.
  4. Storage: every transition (raw event, agent decision, shield execution) writes to SQLite synchronously on the calling thread, wrapped in a short-lived connection per write (SQLite + WAL mode to avoid lock contention across threads).

3. Threading & Concurrency Model

  • Model: classic producer/consumer. Sensors = producers (N threads). Brain = single consumer (1 thread) — deliberately single-threaded so incident correlation has no race conditions.
  • Queue: queue.Queue() (stdlib), bounded size (e.g. 1000) with put(block=False) + drop-oldest-on-full policy, so a flood (e.g., SYN scan burst) can't OOM the process — this is itself a signal (queue-full events are logged as a DoS_SUSPECTED telemetry row).
  • UI thread: CustomTkinter owns the main thread. All background threads communicate to the UI via a second lightweight queue (ui_bus) polled with .after() on a ~100ms tick — CustomTkinter is not thread-safe, so no background thread ever touches a widget directly.
  • SQLite concurrency: PRAGMA journal_mode=WAL; enabled at connection init so sensor threads, the brain thread, and the UI's read-only polling don't block each other.
  • Voice thread: pyttsx3 gets its own dedicated worker thread with a small queue of strings, because the TTS engine's .runAndWait() is blocking and must never stall the brain loop.

4. Ultron Brain ↔ Antigravity Agent Contract

Request (brain → agent): a batched JSON array of correlated telemetry_events rows plus lightweight context (asset criticality flag, repeat-offender count for that IP pulled from incidents).

Response (agent → brain): the agent's system_instructions pin it to return only this JSON shape (validated on receipt; malformed output = treated as a parse failure, logged, and defaults to a conservative Medium manual-review incident rather than silently dropped):

{
  "risk_score": 0-100,
  "severity": "LOW | MEDIUM | HIGH | CRITICAL",
  "mitre_id": "T1110",
  "mitre_tactic": "Credential Access",
  "summary": "plain-English one-liner",
  "recommended_action": "firewall_block | process_kill | quarantine | monitor_only",
  "target_identifier": "ip or pid extracted from the batch"
}

Policy layer: google.antigravity.hooks.policy is configured with deny("*") as the default plus explicit allow() on the two read-only lookup tools (MITRE table, incident history). This is enforced at the SDK level, not just by convention — even if the agent "decides" to call something else, the policy blocks it.

5. OS-Specific Command Handling (Shields)

All OS branching is isolated to a single interface so nothing above shields/ needs to know the host OS:

# shields/base.py — conceptual interface, not code yet
class FirewallShield(Protocol):
    def block_ip(self, ip: str) -> ShieldResult: ...

class ProcessShield(Protocol):
    def kill_pid(self, pid: int) -> ShieldResult: ...
Action Linux Windows
Block IP iptables -A INPUT -s <ip> -j DROP via subprocess.run netsh advfirewall firewall add rule name="ultron_block_<ip>" dir=in action=block remoteip=<ip>
Kill process os.kill(pid, signal.SIGKILL) subprocess.run(["taskkill", "/PID", str(pid), "/F"])
Quarantine host iptables -P INPUT DROP + explicit allow for the management port netsh advfirewall set allprofiles firewallpolicy blockinbound,allowoutbound + allow rule for management port

platform.system() is checked once at startup and a concrete LinuxShield/WindowsShield implementation is selected (strategy pattern) — no if platform == branching scattered through the codebase.

Privilege handling: at startup, shields/privilege_check.py verifies elevated rights (root / Administrator). If missing, the app still boots (detection still works) but the dashboard shows a persistent "SHIELDS DISABLED — run as admin" banner rather than failing silently on the first real block attempt.

6. Non-Functional Requirements

Category Requirement
Latency Detection→containment < 500ms for simulated scenarios; measured with time.perf_counter() at event ingestion and at shield-function return
Resilience Malformed agent output, sensor crash, or DB write failure must not crash the process — each subsystem wraps its loop in try/except with a logger, and restarts its own thread
Data integrity incidents and shield_actions are insert-only from the application layer; no UPDATE/DELETE statements anywhere in the codebase touch historical rows (status transitions insert a new row referencing the old one, or use a status column with an audit trail, not overwrite)
Portability Single config.py flag block for OS-independent paths (pathlib), no hardcoded / or \
Testability Every sensor and shield module exposes a pure-function core (parse/decide logic) separable from its I/O side effects, so unit tests don't require real network/OS access

Folder responsibilities at a glance

Folder Responsibility May call
sensors/ Observe, normalize, enqueue shared/event_bus.py only
core/ Correlate, reason via Antigravity, recommend shared/, database/, read-only tools in core/mitre_lookup.py
shields/ Execute OS-level containment shared/, database/ — never called by sensors/
database/ Persist every state transition nothing above it; pure data layer
range_simulator/ Generate safe test traffic for demo targets sensors/ and shields/ externally, like a real attacker would, not via direct function calls
ui/ Render state, accept human approval clicks shared/ui_bus, shields/ (only on explicit user click in HUMAN_APPROVAL mode)

This mirrors the PRD's module split (God Eye / Ultron Core / Shields / Dashboard) but reorganizes by technical responsibility rather than product-feature name, which is what keeps the core/ package the single, auditable choke point for every action the agent is allowed to trigger.
