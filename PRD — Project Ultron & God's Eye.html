Product Requirement Document

Project Ultron & God's Eye — Autonomous Security Operations Center (SOC) Agent

Version: 1.0 | Type: Hackathon MVP → Production-track platform Status: Approved for build

1. Executive Summary

Ultron & God's Eye is an offline-first, autonomous endpoint and local-network Security Operations Center. It fuses real-time telemetry ingestion (God Eye), AI-driven reasoning powered by the google-antigravity agent SDK (Ultron Core), sub-second automated containment (Autonomous Shields), and a live cyberpunk command dashboard with a built-in attack range for demo-safe validation. The goal is a single running process that can detect, reason about, explain, and neutralize a threat on a local machine/subnet with no cloud dependency for detection or response — only the reasoning layer optionally calls out via the Antigravity/Gemini API.

Demo promise: press a "Simulate SSH Brute-Force" button → watch God Eye detect it → Ultron classify and MITRE-tag it in plain English → Shields block the IP in under 500ms → dashboard shows the whole chain end-to-end.

2. Problem Statement

Traditional SOC tooling (Splunk, QRadar, etc.) is heavy, cloud-dependent, expensive, and reactive — a human still has to read the alert and decide. Small teams and individual machines have no equivalent of an autonomous, explainable, locally-run defense agent that both reasons about intent (via an LLM agent loop) and acts (via OS-level containment) within the same trust boundary.

3. Goals & Success Metrics

Goal Metric
Real-time detection New rogue network asset or canary touch detected within 2s
AI reasoning quality Every incident gets a plain-English summary + correct MITRE tactic tag
Containment speed Detection → Shield action latency < 500ms (displayed live)
Explainability Full chronological, immutable incident timeline reconstructable for any incident
Demo safety All simulated attacks confined to 127.0.0.1 / isolated range, zero risk to judges' network
Autonomy control One toggle switches between fully autonomous response and human-approval-gated response

4. Scope

In scope (hackathon build):

  • Single-host + local-subnet monitoring (God Eye)
  • Antigravity-agent-powered log parsing, scoring, MITRE tagging (Ultron Core)
  • Local firewall/process containment (Shields)
  • SQLite persistence, no external DB dependency
  • CustomTkinter dark/cyberpunk dashboard
  • Loopback-only attack simulator for stage demo
  • Voice alerts via pyttsx3

Out of scope (post-hackathon roadmap):

  • Multi-host distributed swarm coordination
  • Cloud SIEM export / long-term log retention
  • Full computer-vision intruder detection (stubbed as a module hook for v2)
  • Automated PDF/Markdown executive report generation (stubbed as a module hook for v2)

6. Functional Requirements by Module

Module 1 — God Eye (Sensory & Ingestion)

ID Requirement
GE-01 Continuous ARP-based subnet scan (scapy) resolving IP, MAC, vendor OUI lookup; writes to network_assets
GE-02 Flag any newly-seen MAC not present in network_assets.is_authorized as a telemetry event
GE-03 watchdog-based canary file monitor on decoy files in Documents/, Desktop/; on modify/delete, resolve the touching PID via psutil open-file handles within 50ms
GE-04 Honeypot listener on port 21 (and configurable others) via raw socket; any inbound connection = instant telemetry_events row with source_module='honeypot'
GE-05 All three sensors run on independent daemon threads feeding a shared thread-safe event queue consumed by Ultron Core

Module 2 — Ultron Core (Cognition, via google-antigravity)

ID Requirement
UC-01 An Agent (from google.antigravity) configured with system instructions specialized for SOC log triage consumes queued telemetry and returns structured JSON: {risk_score, mitre_tactic, mitre_id, summary, recommended_action}
UC-02 Risk scoring 0–100 mapped to Low/Medium/High/Critical bands, weighted by: attack velocity (events/sec from same source), historical repeat-offender count, and asset criticality flag
UC-03 MITRE ATT&CK auto-mapping table for at least: Brute Force (T1110), Network Service Discovery (T1046), Data Encrypted for Impact (T1486), Exploitation of Remote Services (T1210)
UC-04 Event correlation: events from the same suspicious_ip within a rolling window are merged into one incidents row rather than duplicated
UC-05 On Critical severity, trigger pyttsx3 voice line on a dedicated non-blocking thread
UC-06 Agent policy config uses Antigravity's hooks.policy (deny, allow, ask_user) so the reasoning agent itself never directly executes OS actions — it only recommends; Module 3 executes

Module 3 — Autonomous Shields (Active Defense)

ID Requirement
AS-01 Firewall block: subprocess call to iptables -A INPUT -s <ip> -j DROP (Linux) / netsh advfirewall firewall add rule (Windows), logged to shield_actions with measured latency
AS-02 Process kill: psutil.Process(pid).kill() / os.kill(pid, SIGKILL) on canary-triggering or flagged-malicious PIDs
AS-03 Host quarantine mode: apply a deny-all-except-management-channel firewall ruleset to the local host
AS-04 Response mode toggle in config: AUTONOMOUS (Shields act immediately on Ultron's recommendation) vs HUMAN_APPROVAL (action queued, dashboard shows a "Deploy Shield" button)
AS-05 Every action timestamps entry (detection) and exit (containment complete) to compute and display latency in ms

Module 4 — Cyber Range & Command Center UI

ID Requirement
UI-01 CustomTkinter dark/brass-or-neon cyberpunk shell: network topology panel, live terminal-style event feed, MITRE heatmap grid, camera/voice trigger indicators
UI-02 Range simulator buttons, each spawning a loopback-only (127.0.0.1) scripted attack: SSH brute-force loop, stealth SYN scan, canary encryption burst
UI-03 Live "Defense Latency" readout per simulated attack (e.g., "Neutralized in 140ms")
UI-04 Incident detail view: chronological timeline + (stubbed hook for) evidence relationship graph
UI-05 Natural-language case query box that forwards free-text questions to the Antigravity agent against the SQLite incident store (e.g., "show failed auths from subnet X in last 2 hours")

7. Non-Functional Requirements

  • Offline-first: detection and containment must never depend on network access to function; only Ultron's reasoning call and optional threat-intel lookups (AbuseIPDB/VirusTotal, stubbed for v2) go outbound.
  • Latency budget: end-to-end detection→containment must be demonstrably under 500ms for the simulated scenarios.
  • Safety: all offensive simulation code is hard-locked to loopback/isolated range; no code path can target external IPs.
  • Auditability: incidents and shield_actions tables are append-only from the app's perspective — no update/delete on historical rows.
  • Portability: cross-platform shield commands branch on platform.system().

8. Database Schema (SQLite)

CREATE TABLE network_assets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ip_address TEXT NOT NULL,
    mac_address TEXT NOT NULL,
    vendor TEXT,
    is_authorized BOOLEAN DEFAULT 0,
    first_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_seen TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE telemetry_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source_module TEXT NOT NULL,      -- 'arp' | 'canary' | 'honeypot' | 'auth_log'
    suspicious_ip TEXT,
    raw_payload TEXT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE incidents (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    risk_score INTEGER NOT NULL,
    mitre_tactic TEXT,
    mitre_id TEXT,
    summary TEXT,
    status TEXT DEFAULT 'OPEN',       -- OPEN | CONTAINED | RESOLVED
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE shield_actions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    incident_id INTEGER REFERENCES incidents(id),
    shield_type TEXT NOT NULL,        -- 'firewall' | 'process_kill' | 'quarantine'
    target_identifier TEXT NOT NULL,  -- ip or pid
    latency_ms INTEGER,
    executed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

10. Risks & Mitigations

Risk Mitigation
Firewall commands need elevated privileges Document sudo/admin run requirement; fail gracefully with a dashboard warning if not elevated
Antigravity API call latency could blow the 500ms budget if in the critical path Keep classification async/non-blocking for the detection event; the 500ms metric measures Shield action latency specifically, not the AI call
Judges' machine differs from dev machine (Windows vs Linux) Abstract all OS-specific shield commands behind a single interface, test both branches
Canary/PID resolution race condition Poll psutil open file handles immediately on the watchdog callback, before the triggering process can exit

11. Hackathon Milestones

  1. Hour 0–2: DB schema + folder scaffold + God Eye sensors running standalone, writing to SQLite
  2. Hour 2–5: Ultron Core wired to google-antigravity, consuming the event queue, producing scored incidents
  3. Hour 5–8: Shields module wired to incidents, latency measured and logged
  4. Hour 8–11: Dashboard UI + Range simulator wired end-to-end
  5. Hour 11–12: Dry-run full demo loop, polish voice alerts and MITRE heatmap
